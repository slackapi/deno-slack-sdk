# AGENTS.md

Guidance for agents working in this repository. This is a Deno SDK for building
Slack workflow apps (functions, workflows, triggers, datastores, and the app
manifest).

`README.md` and `.github/` already cover usage, the quickstart, contributing,
releases, and the PR/issue templates. Do not duplicate them here; link instead.
See the [SDK docs](https://docs.slack.dev/tools/deno-slack-sdk/) for API
reference and guides.

## Writing style

- Do not use em dashes anywhere: prose, code, comments, commit messages, or PR
  text. Use a regular hyphen, "i.e."/"e.g.", or parentheses instead. Nothing
  enforces this on Markdown outside `deno fmt` scope, so hold the line manually.
- Write self-explanatory code. Do not add comments that restate what the code
  does; comment only to explain a non-obvious edge case or the reason behind a
  decision.
- JSDoc on the public `Define*` factories is consumer-facing API documentation,
  not inline how-it-works commentary, so it stays.

## Code conventions

- Extend the existing `Define*` generic-factory pattern for builder APIs: the
  factory returns a class that `implements` an `I*` interface and exposes an
  `export()` method returning the manifest schema. Mirror the nearest neighbor
  (`src/datastore/mod.ts` and `src/types/mod.ts` are clean templates).
- Filenames are `snake_case.ts`; module barrels are `mod.ts`; co-locate tests as
  `<name>_test.ts`.
- Use `import type` for type-only imports and keep value and type imports
  separate. Keep explicit `.ts` extensions on relative imports. Use `as const`
  maps to derive schema enum union types.

## Verifying changes

- Run `deno task test` before finishing; this is the gate CI enforces. It chains
  `deno fmt --check`, `deno lint`, the bundle script, and the test suite.
- Run a single test with
  `deno test --allow-read --allow-run <file> [--filter "<name>"]`. Collect
  coverage with `deno task coverage`.

## Test mechanics

- Use `Deno.test`, grouping related cases with `t.step`. There is no BDD
  (`describe`/`it`) style in this repo.
- Import assertions and mocks from `src/dev_deps.ts`, never from a raw std URL.
  Mock with `mock.spy`/`mock.stub` and call `.restore()` in a `finally` block.
- Type behavior is tested, not just runtime values: use `assert<IsExact<...>>`
  and `IsAny`, plus the helpers in `src/test_utils.ts`
  (`assertEqualsTypedValues`, `CanBe`/`CannotBe`). Type-level changes must ship
  with type-level tests.

## Repo-specific traps

- Files under `src/schema/slack/functions/` are autogenerated (note the banner
  at the top). Regenerate them with the generator in
  `src/schema/slack/functions/_scripts/` (see its README); never hand-edit.
- Centralize external imports: runtime dependencies in `src/deps.ts`, test-only
  dependencies in `src/dev_deps.ts`. Lint does not catch raw `jsr:`, `npm:`, or
  `https:` imports elsewhere, so this convention is on you to uphold.
- The public API is the top-level exports of `src/mod.ts` and `src/types.ts`
  only; everything else is internal and unstable. Adding to those files is a
  semver-relevant change (see the "Versioning" section of `README.md`).

## Commits and PRs

- Human-authored commits follow Conventional Commits (`feat:`, `fix:`, `chore:`,
  `ci:`, `docs:`) and include the `Co-Authored-By` trailer.
- Apply the appropriate `semver:major|minor|patch` label to each PR.
- Open PRs using `.github/PULL_REQUEST_TEMPLATE.md`. For the full contribution
  and release process, see `.github/CONTRIBUTING.md` and
  `.github/maintainers_guide.md`.
